# Databricks Asset Bundles (DAB) — Developer Reference

A practical knowledgebase for developers starting out with Databricks Asset Bundles (DABs, recently rebranded "Declarative Automation Bundles"). Source: <https://docs.databricks.com/aws/en/dev-tools/bundles/>.

---

## 1. What a DAB Is

A DAB is an infrastructure-as-code definition of a Databricks project. It bundles, in YAML alongside source code:

- **Source files** — notebooks, Python scripts, wheels, SQL, dbt projects.
- **Resources** — jobs, pipelines, model serving endpoints, dashboards, schemas, volumes, apps, etc.
- **Configuration** — workspace targets, variables, permissions, run identity.
- **Tests** — unit / integration tests run as part of the bundle.

Use a DAB when you need versioned, reproducible deployments across `dev` / `staging` / `prod` workspaces; team collaboration with code review; or CI/CD for Databricks workloads.

**Prerequisites**

- Databricks CLI **v0.218.0 or higher** (`databricks --version`).
- Workspace files enabled (default on Runtime 11.3 LTS and above).
- Configured workspace authentication (OAuth U2M for local dev; service principal / OAuth M2M for CI/CD).

---

## 2. Project Structure

A typical bundle generated by `databricks bundle init`:

```
my_bundle/
├── databricks.yml              # Root config: bundle, targets, includes
├── resources/                  # Resource definitions (jobs, pipelines, …)
│   ├── jobs.yml
│   └── pipelines.yml
├── src/                        # Notebooks, Python modules, SQL
├── tests/                      # Unit / integration tests
├── .gitignore
└── README.md
```

`databricks.yml` is the entry point. Other YAML files are pulled in via `include:` so the project can be split by concern.

## 3. `databricks.yml` — Top-Level Mappings

| Mapping | Purpose |
|---|---|
| `bundle` | Bundle metadata: `name`, optional `databricks_cli_version`, `git`, `cluster_id`, `deployment`. |
| `include` | Glob patterns pulling in other YAML files. |
| `variables` | Custom parameters used via `${var.x}`. |
| `workspace` | Workspace `host`, `profile`, `root_path`, `artifact_path`, `state_path`. |
| `artifacts` | Build instructions for wheels and other artifacts. |
| `resources` | Jobs, pipelines, models, dashboards, etc. |
| `sync` | `include` / `exclude` patterns controlling which local files are uploaded. |
| `permissions` | Bundle-wide permissions applied to all supported resources. |
| `run_as` | Identity used to run jobs/pipelines (`user_name` or `service_principal_name`). |
| `presets` | Convenience defaults (e.g. `name_prefix`, `trigger_pause_status`). |
| `targets` | Deployment environments (`dev`, `prod`, …). Exactly one is `default: true`. |

Minimal example:

```yaml
bundle:
  name: hello_bundle

include:
  - resources/*.yml

targets:
  dev:
    mode: development
    default: true
    workspace:
      host: https://my-workspace.cloud.databricks.com

  prod:
    mode: production
    workspace:
      host: https://my-workspace.cloud.databricks.com
      root_path: /Workspace/Shared/.bundle/${bundle.name}/${bundle.target}
    run_as:
      service_principal_name: 11111111-2222-3333-4444-555555555555
```

### Substitutions

Use `${...}` to reference values:

- `${bundle.name}`, `${bundle.target}`
- `${workspace.current_user.userName}`, `${workspace.current_user.short_name}`
- `${var.<name>}`
- `${resources.jobs.<key>.id}`, `${resources.pipelines.<key>.id}`

Resolve all substitutions and inspect the merged config with:

```bash
databricks bundle validate --output json -t <target>
```

## 4. Resources

Resources live under the `resources:` mapping. Each resource has a unique key used elsewhere via `${resources.<type>.<key>.id}`.

### Common Resource Types

| Type | Purpose |
|---|---|
| `jobs` | Workflows with one or more tasks, schedules, triggers. |
| `pipelines` | Lakeflow Spark Declarative Pipelines. |
| `clusters` | Reusable all-purpose clusters. |
| `experiments` | MLflow experiments. |
| `registered_models` | Unity Catalog ML models. |
| `model_serving_endpoints` | Real-time inference endpoints. |
| `schemas`, `volumes`, `catalogs` | Unity Catalog objects. |
| `dashboards` | AI/BI dashboards. |
| `alerts` | SQL alerts. |
| `quality_monitors` | Lakehouse Monitoring jobs. |
| `apps` | Databricks Apps (Streamlit / Flask). |
| `secret_scopes` | Secret scopes for credentials. |

### Job Task Types

Inside `jobs.<key>.tasks`, each task uses **one** task block:

| Task block | Use for |
|---|---|
| `notebook_task` | Run a notebook. |
| `spark_python_task` | Run a `.py` file on a cluster. |
| `python_wheel_task` | Run an entry point in a built wheel. |
| `sql_task` | Run a query, file, alert, or dashboard on a warehouse. |
| `dbt_task` | Run dbt commands. |
| `pipeline_task` | Trigger a Lakeflow pipeline. |
| `run_job_task` | Trigger another job (`job_id: ${resources.jobs.other.id}`). |
| `condition_task` | Branching with `op`, `left`, `right`. |
| `for_each_task` | Fan-out over a list of inputs. |
| `spark_jar_task` | Run a JAR. |

### Job Example

```yaml
resources:
  jobs:
    daily_etl:
      name: daily_etl_${bundle.target}
      tasks:
        - task_key: extract
          notebook_task:
            notebook_path: ../src/extract.py
          job_cluster_key: main
        - task_key: transform
          depends_on:
            - task_key: extract
          spark_python_task:
            python_file: ../src/transform.py
          job_cluster_key: main
      job_clusters:
        - job_cluster_key: main
          new_cluster:
            spark_version: 15.4.x-scala2.12
            node_type_id: i3.xlarge
            num_workers: 2
      schedule:
        quartz_cron_expression: "0 0 6 * * ?"
        timezone_id: UTC
```

## 5. Variables

Define variables at the bundle level and reference them with `${var.<name>}`.

```yaml
variables:
  catalog:
    description: Unity Catalog target.
    default: main
  notifications_email:
    description: Email for failures.
  cluster_config:               # Complex (object / list) variable
    type: complex
    default:
      spark_version: 15.4.x-scala2.12
      node_type_id: i3.xlarge
      num_workers: 2
  shared_cluster_id:            # Lookup an existing object by name
    lookup:
      cluster: "shared-autoscaling"
```

### Resolution Order (highest priority first)

1. `--var "name=value"` on the command line.
2. `BUNDLE_VAR_<name>` environment variable.
3. `.databricks/bundle/<target>/variable-overrides.json`.
4. Target-specific `variables:` block.
5. Top-level `default:` value.

`lookup:` is supported for `alert`, `cluster`, `job`, `pipeline`, and `warehouse` — it resolves to the object's ID at deploy time, avoiding hard-coded IDs.

## 6. Targets & Deployment Modes

`targets:` defines per-environment overrides. Each target should set `mode:` to either `development` or `production`.

### `mode: development`

- Prefixes resource names with `[dev ${workspace.current_user.short_name}]`.
- Tags resources as dev.
- Marks pipelines as `development: true`.
- Pauses schedules and triggers.
- Allows concurrent job runs.
- Disables the deployment lock (faster iteration).
- Allows cluster overrides via CLI.

### `mode: production`

- Forces pipelines to `development: false`.
- Validates current Git branch matches the target's branch (when configured).
- Requires `run_as` and explicit `permissions` (recommends a service principal).
- Disallows cluster overrides via CLI.
- Requires non-user-specific paths (no `${workspace.current_user...}` in `root_path`).

### Custom Presets

Either mode can be tuned via `presets:`:

```yaml
targets:
  staging:
    presets:
      name_prefix: "[staging] "
      pipelines_development: true
      trigger_pause_status: PAUSED
      jobs_max_concurrent_runs: 1
```

Precedence: explicit resource fields > `presets` > mode defaults.

## 7. Permissions

Two ways to set permissions; **they cannot overlap for the same identity**.

### Top-level (applies to all supported resources)

Levels: `CAN_VIEW`, `CAN_RUN`, `CAN_MANAGE`.

```yaml
permissions:
  - group_name: data-platform
    level: CAN_MANAGE
  - service_principal_name: ${var.ci_sp}
    level: CAN_MANAGE
```

### Resource-level (richer levels per resource type)

```yaml
resources:
  jobs:
    daily_etl:
      permissions:
        - group_name: analytics
          level: CAN_VIEW
        - user_name: oncall@example.com
          level: CAN_MANAGE_RUN
```

Selected per-resource levels:

| Resource | Levels |
|---|---|
| Jobs | `CAN_MANAGE`, `CAN_MANAGE_RUN`, `CAN_VIEW`, `IS_OWNER` |
| Pipelines | `CAN_MANAGE`, `CAN_RUN`, `CAN_VIEW`, `IS_OWNER` |
| Dashboards | `CAN_MANAGE`, `CAN_EDIT`, `CAN_RUN`, `CAN_READ` |
| Experiments | `CAN_MANAGE`, `CAN_EDIT`, `CAN_RUN`, `CAN_READ` |
| Models | `CAN_MANAGE`, `CAN_EDIT`, `CAN_MANAGE_PRODUCTION_VERSIONS`, `CAN_MANAGE_STAGING_VERSIONS`, `CAN_READ` |

### Precedence (highest first)

1. Resource permissions inside a target.
2. Target-level `permissions`.
3. Resource permissions in the bundle root.
4. Top-level `permissions`.

## 8. Authentication

| Scenario | Recommended method |
|---|---|
| Local development | OAuth **U2M** via a CLI profile (`databricks auth login`). |
| CI/CD | OAuth **M2M** with a service principal, or workload identity federation. |
| Legacy | Personal Access Token (PAT) — avoid where M2M is available. |

Switch profiles per command:

```bash
databricks bundle deploy --profile prod-sp -t prod
```

In CI, set credentials via environment variables (`DATABRICKS_HOST`, `DATABRICKS_CLIENT_ID`, `DATABRICKS_CLIENT_SECRET`, etc.) rather than committing them.

## 9. Secure-by-Default Settings

These are the settings every production bundle should explicitly set:

```yaml
targets:
  prod:
    mode: production              # Enforces the prod guardrails described above.
    workspace:
      host: https://...
      root_path: /Workspace/Shared/.bundle/${bundle.name}/${bundle.target}
    run_as:
      service_principal_name: ${var.prod_sp}     # No user-bound runs in prod.
    permissions:
      - group_name: platform-admins
        level: CAN_MANAGE
      - group_name: data-engineering
        level: CAN_VIEW
    git:
      branch: main                # Combined with mode: production, blocks deploys from other branches.
```

**Do**

- Use service principals for any non-interactive deployment or run.
- Reference secrets via `{{secrets/<scope>/<key>}}`; never commit credentials, tokens, or workspace URLs that include tokens.
- Pin a CLI version: `bundle.databricks_cli_version: ">= 0.218.0"`.
- Use `lookup:` for cluster / warehouse / pipeline IDs instead of hard-coding them.
- Store `variable-overrides.json` files in `.gitignore`.
- Set `permissions` on every production resource so access is explicit, not inherited from creator.

**Don't**

- Don't set `mode: development` on shared / production targets.
- Don't put user-specific paths (`${workspace.current_user...}`) under `prod`.
- Don't grant `CAN_MANAGE` to broad groups; prefer `CAN_VIEW` / `CAN_RUN` and reserve manage rights for a small admin group.
- Don't disable the deployment lock outside of dev mode.

## 10. Common CLI Commands

Run from the bundle root:

```bash
databricks bundle init [template]                 # Scaffold a new bundle.
databricks bundle validate -t <target>            # Schema + substitution check. Run before every deploy.
databricks bundle deploy -t <target>              # Upload artifacts and apply resources.
databricks bundle run <resource_key> -t <target>  # Run a job or pipeline defined in the bundle.
databricks bundle summary -t <target>             # Show what is currently deployed for the target.
databricks bundle sync -t <target>                # Sync source files only (faster than full deploy).
databricks bundle generate job --existing-job-id <id>      # Reverse-engineer YAML from a workspace job.
databricks bundle deployment bind <key> <id>      # Attach a YAML resource to a pre-existing workspace object.
databricks bundle destroy -t <target>             # Tear down deployed resources (prompts; --auto-approve to skip).
databricks bundle schema                          # Emit JSON schema for IDE validation.
```

Useful flags:

- `-t, --target <name>` — pick the target.
- `--var "key=value"` — override a bundle variable (repeatable).
- `--profile <name>` — use a specific CLI auth profile.
- `--var-file <path>` — load variable overrides from JSON.
- `-o json` (`bundle validate -o json`) — machine-readable resolved config.

## 11. CI/CD Pattern

A minimal pipeline (any provider) follows this shape per environment:

```bash
# 1. Static check
databricks bundle validate -t prod

# 2. Deploy artifacts and resources
databricks bundle deploy -t prod

# 3. Optionally run smoke tests
databricks bundle run integration_tests -t prod
```

Recommendations:

- One service principal per environment (or one SP with cross-workspace access).
- Authenticate via env vars (`DATABRICKS_HOST`, `DATABRICKS_CLIENT_ID`, `DATABRICKS_CLIENT_SECRET`).
- Run `validate` on PRs, `deploy` on merges to the environment's tracking branch.
- Use `bundle.git.branch` + `mode: production` to block deploys from the wrong branch.
- Treat `databricks.yml` and `resources/*.yml` as code — review them like any other change.

## 12. Best Practices Summary

1. **Split config by concern** — keep `databricks.yml` small; put resources under `resources/*.yml` and pull them in via `include:`.
2. **Parameterize across targets** — use `variables` and target overrides instead of duplicating YAML.
3. **One target per environment** — `dev`, `staging`, `prod`. Set `mode` explicitly on each.
4. **Service principals in prod** — set `run_as` and avoid user-bound execution.
5. **Validate before every deploy** — `databricks bundle validate` is cheap and catches schema, substitution, and reference errors.
6. **Pin the CLI version** in `bundle.databricks_cli_version` so all contributors and CI agree.
7. **Lookups, not IDs** — use `lookup:` to resolve cluster / warehouse / pipeline IDs at deploy time.
8. **Explicit permissions** — set them at the resource or top level; do not rely on creator-implicit access.
9. **Secrets via scopes** — reference with `{{secrets/<scope>/<key>}}`; never commit credentials.
10. **Test `destroy` in dev** — verify teardown is clean before relying on it for ephemeral PR environments.
